Alpine Pi

tags:#blog #alpine-linux #linux. raspberry-pi #self-hosting #hardware

01. introduction

I was watching Zei's new video today where he set up Alpine Linux on a ThinkPad. Installing XFCE, setting up PipeWire, and getting CS2 to run through Flatpak on Alpine is a very different use case than mine, but it reminded me why I appreciate Alpine so much.

Most of my daily computing happens across Fedora, NixOS, and Arch-based systems. Distros like that have massive repositories full of packages and give you bleeding-edge, up-to-date environments. Kernels update quickly, software gets updated constantly, and everything stays fresh. That makes sense for daily workstations where you want recent drivers and new features, but it is the opposite of what I want for a small edge server.

Alpine hits a sweet spot. It gives you the freedom of Linux and the stability of a microwave:

  • Very few packages: A minimal Debian or Fedora install usually starts out with somewhere between 800 and 1,200 packages. This Pi sits around 200 total. Aside from BusyBox, OpenSSH, Tailscale, and Nginx, there just isn't much on the disk. Fewer installed packages simply means fewer updates and security alerts to deal with.
  • Easy on the SD card: Alpine uses musl instead of glibc and OpenRC instead of systemd. There aren't noisy system services or background logging jobs constantly writing away to the flash storage.
  • Appliance feel: It acts a lot like a little hardware router. You turn it on, it sits at 0.00 load, sips a few watts of power, and serves pages from memory without complaint.

Of course, right as I sat down to write about how calm it is, I logged in to check updates. It turns out there were no updates waiting for my version of Alpine because I was still on 3.20. Meanwhile, Alpine 3.24 landed in mid-September. The system had been running so quietly that I had drifted several versions behind without even noticing.

Upgrading in Alpine is straightforward, but jumping across multiple releases at once is asking for trouble. The clean way to do it is stepping through one release at a time. For each version jump, you edit /etc/apk/repositories to point to the next release and run:

apk update && apk upgrade --available

With ~200 packages installed, each version went by in just a minute or two. But it wasn't completely without a hiccup.

When upgrading from 3.22 to 3.23, apk-tools went from version 2.14 to 3.0.8. Version 3 is a major rewrite of the Alpine package manager, and right after that update, apk threw an error:

ERROR: Unable to read database: file format is invalid or inconsistent

The main package database file (/lib/apk/db/installed) was 100% fine. It still read cleanly and accurately listed all 150+ installed packages. The culprit was /lib/apk/db/scripts.tar, an archive file where Alpine keeps older trigger and setup scripts from previous package installs. Version 3 is much stricter about how that archive is formatted than version 2 was, and an old script inside tripped the error. Moving that archive file out of the way allowed apk to read the database again and finish the upgrades cleanly to 3.24.

A quick reboot at the end, and the box is fully up to date. It's nice having a machine on the home network that just does its job without constantly begging for attention. Thanks to Zei for the nudge to actually check the version string.
